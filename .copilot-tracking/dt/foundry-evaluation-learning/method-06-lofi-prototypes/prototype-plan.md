# Method 6 prototype plan

## Current phase

Prototype planning, approved on 2026-11-07. The selected concept is Run Understand Customize; see `../method-05-user-concepts/method-06-handoff.md`.

No prototype has been tested. These are coach-proposed formats for collaborative selection, not completed variations or learner evidence. Keep them rough and small; do not write production lab modules or invoke models at this stage.

## First assumption

A learner with basic Foundry knowledge but little evaluation practice can explain why a domain rubric adds value after inspecting a simple built-in evaluation result.

This is an assumption, not a finding about the audience. Test this distinction first rather than attempting to validate the entire track in one session.

## Candidate variations

| Variation | Format and materials | Single assumption tested |
|---|---|---|
| Action first | Short numbered text walkthrough with placeholders for input, result, and next action | Performing the built-in run before the explanation makes the built-in/rubric distinction understandable. |
| Prediction first | Same inputs with a prompt to predict what the built-in check measures before revealing a human-authored sample result | Predicting the check's scope makes the built-in/rubric distinction understandable. |
| Compare first | Two rough text cards describing built-in and domain checks beside the same supplied answer | A side-by-side comparison makes the built-in/rubric distinction understandable. |

All three keep the approved simple built-in run before rubric generation. Any sample result used in a text prototype must be labelled human-authored and illustrative, not captured Foundry output. Do not invent a guaranteed score contrast.

Build each chosen variation in minutes, not days. These alternatives are not three separate full labs.

## Proposed observation task

Ask a participant to walk through one rough opening and explain which requirement needs a domain criterion rather than the selected built-in check. Do not prompt the desired answer during observation.

Proposed success evidence: the participant identifies the distinction and the next action without facilitator correction. Record misunderstandings and requests for help; do not treat agreement with the coach as success. The test procedure and threshold are proposals pending review.

## Participants and setting

Recruit people with the intended basic Foundry knowledge, including someone without Python-authoring experience. Seek consultant, delivery-engineer, and architect perspectives, plus facilitator feedback. No participant is confirmed.

Use the intended workshop reading environment when possible. Observe navigation, terminology, text accessibility, and interruptions. Record real access or device constraints only when observed; do not invent them.

## Evidence capture and limits

For each test, record the hypothesis, variation, participant role, environment, observed behavior, constraint category, severity, and assumption status. Keep identities out of repository notes.

Create test observations and constraint discoveries when evidence exists. No Method 7 handoff is ready. A text walkthrough tests understanding, not actual Foundry execution or the less-than-two-hour target.
